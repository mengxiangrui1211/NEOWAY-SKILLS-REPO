# 飞书项目需求分析 Skill

通过 `meegle` CLI 查询飞书项目（Meegle / Lark Project）工作项，并可继续做**需求拆解 + 当前仓库源码定位**，输出候选改动点与调用链。

> 只拿到单子需求是不够的：需求分析必须落到代码上。本技能的价值在于「查单 → 拆解 → 定位改动点」一次跑通，且代码定位用通用检索法，换仓库不失效。

## 前置条件

- 本地已安装 `meegle` CLI（`meegle --version` 可输出版本号）
- 已登录（`meegle auth status` 返回 `authenticated: true`）；未登录时先执行 `meegle auth login`
- 源码分析环节需要当前工作目录是一个代码仓库（有可检索的源码文件）

## 触发用法

| 用法 | 用户说 | Agent 做什么 |
|------|--------|-------------|
| **只查单** | "查一下 7105383167" / "飞书项目单 XXX" / "meegle 单子 XXX" | 走 Step 1-4 → Step 4.5 询问是否继续分析 |
| **查单 + 分析（全流程）** | "分析需求单 7105383167" / "这个单子要改哪些代码" / "结合代码分析下这个需求" / "定位改动点" | 跳过 Step 4.5 的询问，直接 Step 1-7 |
| **已有单子信息，直接分析** | 用户贴了需求描述/标题，或上文刚查过单 | 跳过 Step 1-3，从 Step 5 开始 |

## 强制标准流程

### Step 1: 提取工作项 ID

从用户输入中提取数字形式的工作项 ID（如 `7105383167`）。

- 用户可能说"飞书项目单 7105383167""查一下 7105383167""meegle 单子 7105383167"等，提取其中的纯数字即可。
- 如果用户未提供工作项 ID，用 AskUserQuestion 询问。

### Step 2: 获取项目列表（自动发现 project_key）

执行以下命令获取用户可访问的项目空间列表：

```bash
meegle project search -o json
```

解析返回的 `projects` 数组，每个元素包含 `project_key`、`name`、`simple_name`。

### Step 3: 查询工作项

遍历 Step 2 获取的项目列表，依次尝试：

```bash
meegle workitem get --project-key <project_key> --work-item-id <work_item_id> -o json
```

**关键逻辑**：
- 按项目列表顺序逐个尝试，直到找到包含该工作项的项目（返回 `work_item_attribute` 不为 null）。
- 如果所有项目都返回空，告知用户"未找到该工作项，可能无权限或单号不存在"。
- **不要猜测 project_key**，必须从 Step 2 的实际返回中获取。

### Step 4: 格式化输出

从返回的 JSON 中提取关键信息，按以下格式展示：

```
**单号**: <work_item_id>
**标题**: <work_item_name>
**类型**: <work_item_type.name> / <template.name>
**优先级**: <priority.label>
**状态**: <work_item_status.name>

**当前节点**: <work_item_current_node[0].name>
**当前负责人**: <current_status_operator>

**创建人**: <create_by.name> (<create_time>)
**最后更新**: <updated_by.name> (<update_time>)

**问题描述**:
> <description>

**关键角色**:
| 角色 | 人员 |
|------|------|
| <role_name> | <member_name> |
```

**角色展示规则**：
- 只展示有成员的角色（`members` 数组非空）
- 跳过空角色（无 members 或 members 为空数组）
- 如果角色过多（> 10 个），只展示核心角色（PM、SE、项目经理、FAE、当前负责人相关）

**可选扩展**：如果用户要求看更多字段，可在 Step 3 的命令中加 `--fields _all` 查询全部字段。

### Step 4.5: 询问是否继续需求开发分析

**分两种情况，不要一律询问：**

- 用户**一开始就明确要分析**（说了"分析""拆解""要改哪些代码""结合代码分析"等）→ **跳过本步**，直接进 Step 5。
- 用户**只是查单** → 用 **AskUserQuestion** 询问：

  > 单据已查到，是否继续需求开发分析？

  | 选项 | 含义 |
  |------|------|
  | 继续分析（推荐） | 需求拆解 + 当前仓库源码定位改动点，走 Step 5-7 |
  | 到此为止，只看单据 | 结束，不分析 |
  | 只做需求拆解，不查代码 | 只走 Step 5，跳过 Step 6-7 |

- 用户选"到此为止"则正常收尾，**不追问、不擅自开始分析**。

> ⛔ **代码分析范围声明**：源码分析一律在**当前工作仓库（cwd）内**进行。**禁止在本技能正文写死任何具体仓库、目录或机型**。仓库结构千差万别，定位靠下面的通用检索法，不靠记忆中的目录。

### Step 5: 需求拆解

**为什么做**：单子描述是客户/测试语言（如"TCP 断了没重连"），不能直接拿去搜代码。必须先提炼成结构化的"检索线索 + 验收点"，否则 Step 6 只能瞎猜关键词、反复 Grep 落空。

**做什么**（纯阅读 + 结构化，无需命令）：读 Step 4 拿到的 `work_item_name` / `description` / 类型 / 优先级 / 当前节点，产出四张表：

| 拆解项 | 从单子哪里来 | 产出 |
|--------|-------------|------|
| **功能点** | 标题动词 + 描述中的行为描述 | 编号 FP-1 / FP-2…，每条一句话「谁在什么条件下做什么」 |
| **影响范围** | 描述提到的模块/功能/协议/指令/配置 | 模块清单 + **原文引用**作推断依据 |
| **验收点** | 描述中的期望行为、"应该/需要/要求"句式 | 编号 AC-1 / AC-2…，可验证的句子 |
| **疑点** | 描述缺失/含糊/自相矛盾处 | 编号 Q-1 / Q-2… |

**Step 5 → Step 6 衔接物：检索线索表**（把单子字段翻译成可 Grep 的词）

| 单子内容形态 | 检索线索类型 | 示例（示意） |
|-------------|-------------|-------------|
| 引号内的命令字 / 指令 / 协议字段 / 日志文案 | **字面量**（原样带引号搜） | `AT+XXX`、`+CME ERROR`、某字段名 |
| 功能动词 + 名词（"重连""注册""超时"） | **接口名/函数名候选**（中英文同义词各一轮） | `reconnect` / `re_connect` / `重连` |
| 参数名 / 配置项 / 错误码 / 宏 | **符号精确搜** | `CFG_XXX`、`ERR_XXX`、配置键名 |
| 模块名 / 产品特性名 | **目录/文件名 Glob** | `**/*<模块名>*` |

**红线（职责边界）**：
- ✅ 只做「提炼 + 列疑点」
- ❌ **禁止替用户定需求**：缺失的信息一律列为疑点，不编造
- 疑点必须用 **AskUserQuestion** 向用户确认，答案回填进拆解表并标注「用户确认于 \<日期\>」

### Step 6: 源码定位与分析

**为什么做**：需求分析不能脱离代码——影响范围是否属实、改动点在哪、有没有现成实现，都要以代码为证。本步产出「候选改动点 + 证据链」供用户拍板。

**做什么**（用 Grep / Glob / Read，全部在 cwd 内）。

**通用检索入口（3 种，按线索类型选用，从上往下试）**：

1. **字面量检索**（最高优先——用户可见的字符串不会骗人）
   ```
   Grep pattern="<命令字/错误文案/日志文案>" path="<cwd>" output_mode=content
   ```
2. **符号检索**（接口名/函数名/宏/配置项）
   ```
   Grep pattern="<符号名>" type=<c|py|js|go|...> output_mode=content
   ```
   同义词与命名风格变体（下划线、驼峰、缩写）**各来一轮**，一轮 0 命中不许下结论（见坑表）。
3. **文件名/目录兜底**（线索只有模块名、符号搜不到时）
   ```
   Glob pattern="**/*<关键词>*"
   ```
   找到疑似模块目录后，再在该子目录内做入口 1/2 缩范围。

**标准动线（必须按序）**：

1. 从 Step 5 的检索线索表逐条发起检索（先字面量、后符号、最后 Glob）。
2. Grep 命中 → **Read 命中文件的上下文**（前后约 30 行），确认命中的是「实现」还是「注释 / 测试 / 废弃代码」。
3. **确认调用链 / 注册点**：对关键函数名再 Grep 一次，找**调用点与注册点**（命令分发表、表驱动注册、switch 分发、初始化注册函数——按仓库实际形态识别，**不写死**）。调用链走 1-2 层即可，标注「上游入口 → 本函数」。
4. 每个候选改动点记录四元组：

   `文件:行号 | 现状代码语义 | 与需求的差距 | 证据（单子原文/用户确认）`

**坑表**：

| 坑 | 正确写法 | 错误后果 |
|----|---------|---------|
| 0 命中就断言"代码里没有" | 换 2-3 轮同义词/命名风格再下结论，并注明「未检索到，可能关键词不匹配」 | 错误结论"无实现"，误导开发决策 |
| 大仓库裸 Grep 全仓 | 带 `type` / `glob` 过滤（如 `*.c`、`src/**`），必要时先 Glob 缩到子目录 | 检索超时 / 噪声淹没真命中 |
| 把注释/测试/废弃代码当实现 | Read 上下文确认语义，标注命中性质 | 改动点定位到错误位置 |
| 在技能正文写死仓库专有路径 | 一律用相对 cwd 的通用检索法 | 技能换仓库即失效 |
| 需求含糊直接开搜 | 先走 Step 5 疑点确认（AskUserQuestion） | 搜错方向，整轮分析作废 |

**红线（职责边界）**：
- ✅ 只给**候选改动点与证据链**
- ❌ **本技能不执行任何代码修改**；改不改、怎么改由用户拍板

### Step 7: 汇总结论 + 落盘

**为什么做**：用户要「对话里拿到结论 + 留档复用」。分析做完必须同时给两份产出，且落盘路径可预期（下次同单号能找到上次的分析）。

**执行什么**：
1. 对话里输出「对话输出模板」（见下）。
2. 按「分析文档落盘规范」把完整分析写入 markdown 文档（Write 工具，目录不存在时创建）。
3. 对话末尾告知落盘路径，并问下一步：「要继续细化哪个改动点 / 直接开始改代码？」

## 分析文档落盘规范

**路径规则**：

```
docs/nwy-<序号>-<短名>.md
```

- 示例：`docs/nwy-001-TCP断开重连.md`、`docs/nwy-002-短信白名单鉴权.md`
- **目录**：默认落在 `docs/` 下，**不要写死更深的子目录**
- `<序号>`：3 位补零流水号 —— 扫描 `docs/` 下已有 `nwy-<数字>-*.md` 取**最大序号 +1**；一个都没有则从 `001` 起
- `<短名>`：**由 agent 根据需求内容自动生成**的简短名字（提炼需求核心动作，≤12 字；空格转连字符，去掉特殊符号）。不要用单号当短名
- **重跑规则**：
  - 先在 `docs/` 里搜该单号，**已有报告就复用那个文件覆盖更新，不分配新序号**
  - 没有才分配新序号新建
  - 用户已确认的疑点结论，重跑时**必须保留**
- `docs/` 不存在则创建

**报告骨架**：

```markdown
# 需求分析报告 · <单号> <单子标题>

| 项 | 值 |
|---|---|
| 单号 / 类型 / 优先级 / 状态 / 当前节点 | <照抄单据> |
| 负责人 / 创建人 | <照抄单据> |
| 分析日期 | <YYYY-MM-DD> |

## 一、需求原文摘要
> <description 原文，过长可截取关键段并注明>

## 二、需求拆解
### 2.1 功能点（FP-n）
### 2.2 影响范围（含推断依据原文引用）
### 2.3 验收点（AC-n）
### 2.4 疑点与待确认（Q-n，标注用户确认结果与日期）
### 2.5 检索线索表（单子字段 → 检索词）

## 三、源码分析
### 3.1 检索记录（线索词 / 命中数 / 命中性质：实现|注释|测试|废弃）
### 3.2 关键代码位置（文件:行号 + 现状语义）
### 3.3 调用链 / 注册点

## 四、候选改动点结论
| 编号 | 改动点 | 文件:行号 | 现状 → 目标 | 证据 | 风险/影响 | 置信度 |
|---|---|---|---|---|---|---|

## 五、遗留疑点与建议下一步
```

## 对话输出模板（Step 7 引用）

```markdown
## 需求分析 · <单号> <标题>

### 需求拆解
| 项 | 内容 |
|---|---|
| 功能点 | FP-1 <...>；FP-2 <...> |
| 影响范围 | <模块/功能清单>（依据：<原文片段>） |
| 验收点 | AC-1 <...>；AC-2 <...> |
| 疑点 | Q-1 <...>（<已确认:xxx / 待确认>） |

### 候选代码改动点（供拍板，本技能不改代码）
| 编号 | 改动点 | 位置 | 现状 → 目标 | 置信度 |
|---|---|---|---|---|
| C-1 | <...> | <相对路径:行号> | <现状> → <按需求应...> | 高/中/低 |

### 调用链（关键路径）
<上游入口> → <本函数>（<相对路径:行号>）

> 完整分析已落盘：docs/nwy-<序号>-<短名>.md
> 下一步：细化哪个改动点 / 直接开始改代码？
```

**只查单模式下不输出本模板**，仍用 Step 4 的单据模板。

## 错误处理

| 场景 | 处理方式 |
|------|---------|
| meegle 未安装 | 提示 `npm install -g @anthropic/meegle-cli` 或参考内部文档安装 |
| 未登录 | 提示执行 `meegle auth login`，完成后再重试 |
| project search 返回空 | 告知用户无可用项目空间，可能需要申请权限 |
| workitem get 返回 403/权限错误 | 告知用户无该项目的访问权限 |
| 单号不存在 | 告知用户未找到该工作项 |
| 用户在 Step 4.5 拒绝分析 | 正常收尾，不追问、不擅自开始 |
| 需求描述过于简略 | 先 AskUserQuestion 补齐疑点，再进 Step 6 |
| 源码检索 0 命中 | 换同义词/命名风格重试 2-3 轮；仍无则如实报告「未检索到，可能关键词不匹配」，禁止断言"代码里没有" |
| Grep 全仓超时/结果过多 | 加 `type`/`glob` 缩范围，或先 Glob 定位子目录再搜 |
| `docs/` 不存在 | 创建后写入 |
| 同单号此前已分析过 | 同日覆盖、跨日新开；已确认的疑点结论必须保留 |

## 使用示例

### 示例 1：只查单

用户输入：
> 帮我看下飞书项目单子 7105383167

Agent 执行：
1. `meegle project search -o json` → 拿到 3 个项目 key
2. `meegle workitem get --project-key 648a80cd03f4832155473b13 --work-item-id 7105383167 -o json` → 命中
3. 按 Step 4 模板格式化输出
4. **AskUserQuestion**：「单据已查到，是否继续需求开发分析？」→ 用户选「到此为止」则结束

### 示例 2：查单后选继续分析

用户输入同上，但 Step 4.5 选「继续分析」：

5. Step 5 需求拆解 → 功能点 FP-1…、影响范围、验收点 AC-1…、疑点 Q-1（AskUserQuestion 确认）、检索线索表
6. Step 6 按线索表 Grep/Glob/Read → 候选改动点 `相对路径:行号` + 调用链
7. Step 7 对话输出模板 + 落盘 `docs/nwy-001-<按需求内容生成的短名>.md`

### 示例 3：用户直接要求分析

用户输入：
> 分析需求单 7105383167，看下要改哪些代码

Agent 执行：Step 1-4 查单 → **跳过 Step 4.5 询问** → 直接 Step 5-7。
